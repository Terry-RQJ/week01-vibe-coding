## 二、法条核验

本批引用 20 余条法条，全部逐条比对官方全文后才写入。`law(name, text, src_key)` 的签名要求 `src_key` 必须存在于 `SRC` 字典，**写错 key 会直接 KeyError 中断生成**——这个设计就是为了从机制上杜绝「写出一条没核验过出处的法条」。

本批用到的法：
- 民法典：19、20、145、497、509、577、670、680、897、962、964、985、1037、1038、1183、1184、1191、1198、1218
- 个人信息保护法 26（人脸识别的单独同意）
- 消费者权益保护法 26、55
- 电子商务法 38、61
- 反电信网络诈骗法 18、38
- 未成年人保护法 39、74（网络服务提供者的消费管理义务）
- 旅游法 35
- 劳动合同法 9、84（禁止收取押金 / 介绍费）

### 三个踩过的坑（Day 34 遗留教训在本批复现）

1. **`www.gov.cn` 的民法典页面已 404**。改走 `12371.cn` 已经登记的那份全文（470647 字节）。
2. **`12371.cn` 有两个相似地址，其中一个只有 3.4KB 不含正文**。只用项目里已登记、已验证过字节数的那一个。
3. **`npc.gov.cn` 会返回「假成功」**：约 **87917~88007 字节**的响应是统一错误页，HTTP 200 但里面没有内容。判断口径：文件大小落在这个区间一律按失败处理，改换新华网受权发布源。

**`SRC` 没有重复登记未成年人保护法**——它和 Day 34 用的是同一部法、同一个源，直接复用已有 key，只加注释说明。同一部法登记两个出处，以后核对时会变成两个口径。

## 三、核心教训一：假命中可能是「停用表漏词」，不是「卡片写错」

导库部署后跑线上回归，`day29-verify-online.py` 报：

```
[FAIL] 收严门槛 · 无意义长句应为 0 条
       实际返回 2 条
```

探测串是「这是一个绝对不存在的词组」，本该 `mode=none`。命中了两张卡：`heizhongjie` 和 `zhongjiefei-tuihai`。

**第一反应是卡片写错了**——按 Day 34 的经验，假命中通常是 tag 越界或文案主角错位。但打开这两张卡看，正文里确实写着「这是证明他提供虚假情况的关键」「只给了一个面试地址」。**卡片没错。**

继续查 DF（文档频率）：

| 片段 | 出现卡数 / 153 |
|---|---|
| `这是` | 12 |
| `一个` | 15 |
| `就是` / `还是` / `只是` / `也有` / `没有` | 各自也偏高 |

`这是` + `一个` 两个片段都过了召回门槛，凑在一起就把毫不相干的卡拉了出来。**根因是停用表漏了这两个高频虚词，不是内容问题。**

第一轮修复：`STOP_FRAGS` 补 `这是 / 一个 / 就是 / 还是 / 只是 / 也有 / 没有` → 从 2 条降到 **1 条**。

剩下那 1 条命中 `fenju-zidong-lihun`（分居满两年自动离婚那张卡）。再查，来源是 `不存` + `存在`。

### 这里有个容易搞错的地方

`存在` 看着也像虚词，但它在「房屋存在安全隐患」「公司是否存在劳动关系」里是**实词**，停掉会误伤真实搜索。

而 `不存` 只是「不存在」这个固定搭配切片后的残留，既不是词也不是概念。

**结论：停用表按「片段」收，不按「词」收。同一个词的两个切片，可以只停一个。**

补 `不存` 后：线上 `mode=none`、0 条。

### 沉淀成判断规则

遇到「搜无意义串却出结果」，按这个顺序查：

1. 先看命中的卡**本身有没有错**（tag 越界 / 主角错位）——有错就改卡。
2. 卡片没错，就**算每个片段的 DF**，看哪个偏高。
3. 偏高的片段里，**区分实词与虚词**：换了哪张卡都不改变含义的（这是、一个、就是）→ 停用；只在特定语境成立（存在、要求、可以）→ **留着**。
4. 停词的粒度是**片段**，不是词。

## 四、核心教训二：preflight C17 抓到了一个「改了但没生效」

这是本批最值得记的一次。

`STOP_FRAGS` 有两份副本必须同步：
- 前端：`js/store.js`
- 后端：`functions/api/cards/cardsRepository.js`

我改的时候心里记着「两份要同步」，也确实同步了这两份。云函数也部署了，API 回归全绿。

但**漏了第三份**：`dist/js/store.js`——部署到静态托管的那份。

preflight C17「根目录与 dist/ 的 js/css 内容一致」直接报了：

```
[FAIL] C17  根目录与 dist/ 的 js/css 内容一致
        比对 5 项 → !! 不一致: ['js/store.js']
```

对比 MD5 确认：根目录 `3efcb9e8...`，dist `5b76a4ad...`。

**后果**：云函数那侧已修，但网页端加载的是 dist 里的旧表——**用户在浏览器里搜，降噪修复实际一直没生效**。API 回归全绿是因为它测的是服务端，完全测不到这个。

修复：`cp js/store.js dist/js/store.js` → 重部署 → curl 带 `Cache-Control: no-cache` 和 `?t=$(date +%s)` 验证线上确实含 `"不存"` → preflight 重跑 **28/28**。

### 沉淀

以后改任何**前端共享文件**（`js/*.js`、`css/*.css`），同步清单是**三份**：

```
js/store.js                              ← 改这里
functions/api/cards/cardsRepository.js   ← 云函数侧副本
dist/js/store.js                          ← 部署产物，最容易忘
```

或者更稳的做法：改完直接 `cp` 根目录全部前端文件到 `dist/`，再让 preflight C16/C17 兜底。**C17 这条检查就是为这个坑写的，别绕过它。**

## 七、这批的方法论

1. **假命中先分层，再动手**。Day 34 的三种成因（tag 越界 / 主角错位 / 同音粘连）之外，本批加了第四种：**停用表漏词**。前三种要改内容，第四种改词表——改错方向会白改一轮内容。
2. **停用表按片段收**。`不存` 停、`存在` 留，是同一词的两个切片。判断标准是「换了哪张卡都不改变含义」。
3. **`dist/` 是独立的第三份拷贝**，不是链接也不是软链。改了源码不等于改了线上。
4. **验证要分层跑**：API 回归测服务端，e2e 测浏览器，preflight 测「源码与产物是否一致」。**任何一层缺了都会漏**——本批就是 API 全绿但网页端没生效。
