## 2. 根因：三层

### 2.1 门槛公式用错了分母

Day 29 的近似检索：把关键词切成 2 字片段，**任一命中即召回**。
「搬家公司」→ `[搬家公司, 搬家, 家公, 公司]`，「公司」在全站几十张卡的法条里都出现，于是全被捞回来。

第一反应是加门槛（`hits >= ceil(片段总数 × 系数)`），但**分母里混进了永远匹配不上的伪片段**：

```
「楼上老是吵我睡不着」→ 楼上、上老、老是、是吵、吵我、我睡、睡不、不着
                            ↑     ↑     ↑     ↑     ↑     ↑
                          这些跨词粘连的片段 DF 恒为 0，永远命中不了，
                          却把门槛从「凑 2 个」抬到「凑 4 个」
```

系数调到 0.4 时，「楼上噪音太大怎么办」直接漏召回——噪音卡只命中 2 个有效片段，却要凑够 3 个。

### 2.2 法条原文被算进了「这张卡在讲什么」

「装修合同」召回 3 张讲三包/瑕疵举证的卡，原因是消保法条文里有「装饰装修」四个字。
**法条是通用法律文本，不代表卡片主题**——它是「所有卡都有的背景噪声」，参与门槛计数等于给假命中开后门。

### 2.3 排序没有区分度

Day 29 的排序键是 `标题命中片段数 > 命中片段总字数 > 命中片段个数`，外加 `weight = hits × 2`。
没有「命中在哪个字段」的概念——标题里命中一次，和法条正文里命中一次，价值天差地别。

---

## 3. 修复：三个改动 + 一个洞察

### 3.1 核心洞察 —— 用 DF 筛出「真证据」

**文档频率（DF）**：统计每个 2 字片段命中了多少张卡。

- **DF = 0** 的片段：跨词粘连产物，全站一张卡都匹配不上 → **伪片段，出局**
- **DF > 0** 的片段：内容库里真实存在的证据 → **live 片段，门槛只按它算**

这一个筛选同时解决了 2.1 的两个矛盾：

| 场景 | 旧行为 | 新行为 |
|---|---|---|
| 「楼上老是吵我睡不着」 | 8 个片段要凑 4 个 → **漏召回** | live 只剩「楼上」「吵」「睡不着」等，门槛降到 2 → **精准召回 1 条** |
| 「搬家公司」 | 「公司」命中几十张 → **24 条假命中** | live 只有「搬家」「公司」，门槛 2 且必须全中 → **0 条，走空态推荐** |

### 3.2 改动清单

| # | 改动 | 位置 |
|---|---|---|
| ① | `STOP_FRAGS` 停用片段表：剔除「怎么 / 么办 / 可以 / 请问 / 现在 / 一下…」零信息量通用尾巴 | 前后端各一份**完全相同的副本** |
| ② | 门槛按 **live 片段数**动态定：`live<2` 不召回 / `live≤2` 全中 / `live≥3` 取 `ceil(live×0.5)` | `listApprox` 三 CTE（`src` / `df` / `live`） |
| ③ | 门槛计数**排除法条原文**（`hay_core` 不含 laws）；法条仍参与排序但权重最低 | `hay_core` vs `f_laws` 分离 |
| ④ | 排序改**字段加权**：标题×10 / 标签×6 / 摘要·情景×3 / 步骤×2 / 法条×1 | `listApprox` + `localSearch` |
| ⑤ | 精确检索加**相关度分档**：标题 1 > 标签 2 > 摘要·情景 3 > 步骤 4 > 仅法条 5，档内再按日期 + slug | `RANK_EXPR` / `rankExact` |
| ⑥ | 排序比较器补 **slug 兜底** | `byDateDesc`（修前后端首条不一致） |

### 3.3 后端 SQL 形态

```sql
WITH src AS (... 每张卡的 hay_core / f_title / f_tags / f_body / f_steps / f_laws ...),
     df   AS (SELECT f, count(*) AS n FROM src s, unnest($1::text[]) AS f
              WHERE s.hay_core ILIKE '%' || f || '%' GROUP BY f),
     live AS (SELECT f FROM df WHERE n > 0)      -- ← 关键：DF > 0
SELECT ...
FROM src s CROSS JOIN LATERAL (... 按字段分别 count(*) FILTER ... ) m
CROSS JOIN (SELECT count(*) AS n FROM live) lc
WHERE lc.n >= 2
  AND m.hits >= CASE WHEN lc.n <= 2 THEN 2 ELSE ceil(lc.n * 0.5) END
ORDER BY (m.title_hits*10 + m.tags_hits*6 + m.body_hits*3 + m.steps_hits*2 + m.law_hits) DESC,
         m.hits DESC, s.published_at DESC, s.slug
```

SQL 全长 1868 字符，远低于 `MAX_SQL_CHARS = 30000`。

### 探针脚本踩过的两个坑（写在文件注释里了）

1. **别用 `Promise.all(arr.map(x => fn(x).then(r => out.push(r))))` 收集结果**——push 顺序是**完成顺序**而非请求顺序。并发延迟参差时数组被打乱，「第 i 个词」对上「第 i 个返回的结果」，前后端一致性全线飘红（曾 19/29 误报）。改用 `Promise.all` 的返回值，它保证按入参顺序。
2. **`window.fetch` 和 `global.fetch` 必须一起 stub**——`store.js` 里是 `if (!window.fetch)` 检查、却调用**裸** `fetch(...)`。只 stub `window.fetch` 的话，Node 22 的全局 fetch 会顶上来真发请求，「本地测试」跑的其实是线上结果。
