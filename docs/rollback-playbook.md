# 回滚手册 · 法律小科普轻站

> Day 26 产出。**静态托管回退路径已在当天真实演练过两轮**（见 `day26-rollback-drill.md`）；云函数回退与数据恢复按今日边界**只写不实操**，标注「备查」。
> 一句话原则：**先恢复服务，再查原因**——用户面对的是"打不开"，不是"为什么"。

---

## 1. 什么情况必须回滚（判断表）

| 症状 | 严重度 | 判断 | 动作 |
|---|---|---|---|
| 首页打不开 / 白屏，且能确认不是本机网络问题 | 🔴 高 | **立即回滚**，先恢复服务再查因 | 静态托管回退 |
| 页面能开，但核心功能（读卡片/分类）整体挂掉 | 🔴 高 | **立即回滚** | 静态托管回退 |
| 收藏写入报错、数据丢失迹象 | 🟣 极高 | **先停写**（下线写入口），再评估是否回退云函数 | 云函数回退 + 数据备份 |
| 疑似密钥泄露 | 🟣 极高 | **立即作废密钥**，再评估是否回滚受影响版本 | 安全应急（见 security-checklist） |
| 样式错乱 / 个别文案错误，功能可用 | 🟢 低 | **不回滚**，修复后随下一版发布 | 记录到问题清单 |
| 仅单个浏览器 / 单人偶发 | 🟢 低 | 先复现确认，多半是缓存或本地环境 | 记录，不回滚 |
| 新版功能"不想要了"但没坏 | ⚪ 产品决策 | 走正常迭代（改回来），不走应急回滚 | 正常提交 |

**三条铁律**
1. 回滚的目的是恢复可用性，不是找真相——原因查清可以慢，恢复必须快
2. 每次回滚都要留记录（时间、耗时、从哪退到哪、验证结果），这是演练手册能持续可用的前提
3. 回滚本身也要验证——退完不验证等于没退

## 3. 静态托管回退步骤（✅ 已真实演练两轮）

```bash
# ① 从 git 导出目标版本的全部静态文件（不用手工挑文件，一条命令还原）
git archive 8081183 -- index.html card.html bookmarks.html history.html check.html \
  css js data assets .nojekyll README.md | tar -x -C .tmp-rollback

# ② 覆盖部署（--safe 发布前自动备份当前线上，失败自动回退；--verify 校验远端=本地）
tcb hosting deploy ./.tmp-rollback -e rqj-2006-d0gl1ael531a243a1 \
  --ignore .nojekyll --safe --verify

# ③ 验证（必须绕 CDN 缓存，否则看到的是旧缓存）
curl -s -H "Cache-Control: no-cache" \
  "https://rqj-2006-d0gl1ael531a243a1-1497985433.tcloudbaseapp.com/?cb=$(date +%s)" \
  | grep "期望在旧版出现的特征文案"
#   同时确认新版特征已消失：
#   ... | grep -c "ver-badge"   → 应为 0

# ④ 问题修复后，恢复新版
tcb hosting deploy ./dist -e rqj-2006-d0gl1ael531a243a1 \
  --ignore .nojekyll --safe --verify
#   再跑一遍 ③，确认版本标记回来了
```

**实测耗时**：回滚部署 8~11 秒，CDN 生效后再 9~18 秒，**公网恢复可用全程 < 30 秒**；一次完整演练（回滚→验证→恢复→再验证）约 1 分钟。

**为什么验证要看"两个方向"**：既要确认「旧版特征出现了」，也要确认「新版特征消失了」。只查前者会被 CDN 缓存骗过（缓存里还是新版，恰好也含旧版没有的东西时容易误判）。

## 4. 云函数回退步骤（📋 备查，今日未实操）

> 触发条件：写接口报错、数据异常、接口整体 5xx，且确认是函数代码问题（看 `docs/` 下当天的部署记录定位是哪天改的）。

```bash
# ① 从 git 取回好版本的函数代码（只还原 functions/，别把静态文件混进来）
git checkout 8081183 -- functions/

# ② 重新部署（四个函数互相独立，坏哪个补哪个；也可以 --all 全量）
tcb fn deploy apiCards      -e rqj-2006-d0gl1ael531a243a1 --force
tcb fn deploy apiCategories -e rqj-2006-d0gl1ael531a243a1 --force
tcb fn deploy apiFavorites  -e rqj-2006-d0gl1ael531a243a1 --force
tcb fn deploy apiHealth     -e rqj-2006-d0gl1ael531a243a1 --force

# ③ 验证：/api/health 先行，再按 api-contract.md 逐接口核对
# ④ 注意：跨函数共用文件（errors.js / db.js）是「母版 + 四目录副本」结构，
#    回退时必须四份一起回，否则部署会因副本不一致出问题（Day 22 坑）
# ⑤ 搞定后 git checkout main -- functions/ 把工作树恢复到最新，避免下次部署带旧代码
```

## 5. 数据恢复（📋 备查，今日未实操）

| 数据 | 在哪 | 丢了的后果 | 恢复方式 |
|---|---|---|---|
| 用户收藏（`favorites`） | 用户浏览器 localStorage + 云端表 | 用户重新收藏即可，**损失极小** | 云端表从发布前导出的 JSON 重灌（注意 `is_deleted` 与部分唯一索引 `uq_favorites_active`） |
| 内容（`cards`/`categories`） | 云端表 | 页面没内容 | **源头在仓库** `data/cards.js` + 文档，可全量重建，不需要"恢复" |

- 备份动作（每次发布前）：`tcb db execute --sql "SELECT * FROM favorites"` 导出 JSON 存本地
- ⚠️ 查询返回的 JSON 形状别凭记忆猜（顶层是数组还是 `data.Rows` 曾踩过坑），**以实际返回为准**
- localStorage 的用户数据不在服务端备份范围内——这是纯前端架构的既定取舍（PRD §8.3）
