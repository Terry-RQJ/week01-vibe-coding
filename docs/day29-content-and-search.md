### 2.1 唯一内容源机制（防「两份副本走偏」）

此前 `db/seed.sql`（入库）与 `data/cards.js`（离线回落）是**两份手写副本**，Day 28 已出现

db/seed-content.py  ──生成──▶  db/seed.sql     （tcb db execute 入库）

改内容 = 改脚本 → 重新生成 → 导库，两份副本从机制上不可能再走偏。

## 3. 搜索三段式（后端，`/api/cards`）

| 阶段 | `meta.matchMode` | 触发 | 行为 |
|---|---|---|---|
| ① 精确 | `exact` | 整串命中 | 与 Day 17 语义一致 |
| ② 近似 | `fuzzy` | ① 为 0 条 | 关键词切成 2 字滑窗片段，**任一命中即召回** |
| ③ 无 | `none` | ② 也为 0 | `data: []`，前端展示「为你推荐」 |

近似排序（`cardsRepository.listApprox`，`CROSS JOIN LATERAL` 打分）：

```
ORDER BY 标题命中片段数 DESC, 命中片段总字数 DESC, 命中片段数 DESC, 发布时间 DESC
```

> 「公司不给加班费」若不看标题命中数，会因发布时间新把「不签劳动合同」排在「加班费」前面——实测踩到后修正。

**无关键词时响应与 Day 17 逐字段一致**（不新增 meta 字段），老调用方零影响。

## 4. 「直接查到法条」：`meta.matchedLaws`

搜「劳动合同法」时卡片标题里并没有这五个字（命中的其实是法条原文），必须把条文摊开给用户看。
`matchedLaws`（≤12 条）的取数有**两条来源，缺一不可**：

1. **法条自身的名称/原文命中关键词** —— 搜「劳动合同法」「彩礼」「利息」走这条；
2. **本次命中卡片所关联的全部法条** —— 搜「押金」走这条。

> 为什么必须有第 2 条：法条原文里根本没有「押金」二字（民法典 714 条写的是「租赁物转租」）。
> 只按第 1 条取数，用户会看到「搜到了情形、法条区却是空的」——第一版实现正是这样，线上实测抓出后补上。

排序三档：法条自身命中的在前 → 其余按「命中卡片的相关度顺序」（`array_position($2, l.card_slug)`）→ 同卡内按 `sort_order`。
同一条法条被多卡引用时前端按「条名+原文」去重。

## 6. 顺手修掉的执行器环境坑（`db/exec.py`）

导库时踩到两个**之前 6 张卡时代暴露不出来**的坑：

1. **cmd.exe 8191 字符上限**：`tcb.cmd` 是批处理 shim，必须经 cmd.exe 解析；24 张卡的
   INSERT 压平后 10960 字符，被截断，CLI 回一句 GBK「命令行太长」——还被 utf-8 解码器
   吞掉，表现为「无理由失败」。**解法：用 node 直跑 CLI 的入口 js**（`@cloudbase/cli/bin/tcb`），
   绕开 cmd.exe（CreateProcess 上限 32767，宽裕 4 倍）。
2. **CLI 报错是 GBK 编码**：改二进制读 + 「先 UTF-8 严格、失败回落 GBK」解码，两边都不乱码。
3. `TCB_CLI` 探测列表补上 CLI 实际安装位置（`node/workspace/node_modules/.bin/`）。

## 8. 取舍与已知妥协（诚实记录）

1. **中文长句几乎必然命中近似结果**：「一个」「存在」这类高频 2 字片段总会命中几张卡，
   这是「长句兜底」的必然推论。判定标准改为：纯拉丁串（如 `zzqqxx`）才可能 `none`。
   与其让用户 0 结果（回到「搜索坏了」的原点），宁可给近似结果 + 明确提示。
2. **fuzzy 有召回噪音**：靠三档排序把最相关的顶到最前，前端截断展示 6 条 + 黄色提示条管理预期。
   未做停用词表 / IDF 加权——24 张卡的语料收益不确定，复杂度先不上。
3. **matchedLaws 上限 12 条**：够铺满一屏，避免响应膨胀；同一法条多卡引用会去重。
4. **民法典出处用共产党员网**（中央组织部主办）而非人大网：人大网只有主席令页无全文，
   政府网只有命令/新闻，属如实标注的官方替补源。
