## 三、核心：同一轮三种假命中，三种根因

这轮最有价值的发现，是 `day29-verify-online.py` 的「无意义长句」检查连续失败三次，但**每次根因都不一样**。如果一律按「停用表漏词」处理，会越改越错。

### 起因

加完 10 张卡后线上回归报：

```
[FAIL] 收严门槛 · 无意义长句应为 0 条（不再是长句兜底）
测试串：「这是一个绝对不存在的词组」→ mode=fuzzy，召回 1 条
```

### 排查

先算片段、再逐张对：

```sql
SELECT f, count(*) n FROM cards c,
  unnest(ARRAY['这是','是一','一个','个绝','绝对','对不','不存','存在','在的','的词','词组']::text[]) f
WHERE c.slug='chezhu-yiwo'
  AND (hay_core ILIKE '%'||f||'%') GROUP BY f
```

命中：**`绝对`（1）** 和 **`对不`（1）**。

来源是这张卡第 4 条步骤原文：「**绝对**不要自己锁车、扎胎、拖车」——`绝对` 命中，`对不` 是「绝对不要」切出来的。

`live=2`，门槛 = 2，两个片段都命中 → 召回。测试串里恰好也有「绝对」和「对不」。

### 关键判断：这是真词，不能进停用表

| 片段 | 能停吗 | 理由 |
|---|---|---|
| `这是`、`一个`、`就是`（Day 35 停掉的） | ✅ 能 | 纯语法词，换了哪张卡都不指向具体场景 |
| `绝对` | ❌ **不能** | 是实打实的副词。「绝对不起诉」「绝对免责条款」这类正常搜索会被误伤 |
| `对不` | ⚠️ 单独停没用 | 它是 `绝对` 的切片，`绝对` 还在，只是换成别的死法 |

**停用表只收「换了哪张卡都不改变含义」的片段。`绝对` 不是。**

### 解法：改文案，不是改表

把「绝对不要自己锁车」改成「千万别自己锁车」。语气没变（甚至更口语），`绝对` 和 `对不` 两个片段同时消失，测试串重新落回空态。

验证：`mode=none`、0 条，线上验收 37/37。

## 四、三种根因的对照表

这轮 + 前几轮的教训，整理成四种成因。**遇到假命中先分型，再动手**：

| 成因 | 症状 | 解法 | 典型案例 |
|---|---|---|---|
| ① tag 越界 | 卡的 tags 里写了卡本身没讲的事 | 删 tag | Day 33 装修卡写了「装修押金」；**Day 36** `chewei-gui-shui` 写了「占车位」但讲的是归属 |
| ② 文案主角错位 | 场景描述里出现别的话题关键词 | 改文案 | Day 34「租房中介」 |
| ③ 同音字 / 固定搭配粘连 | 片段在别处凑巧重合 | 补内容 + 白名单过渡 | Day 34「账号被封」命中「账号被盗」 |
| ④ 停用表漏虚词 | 高频纯语法词凑够门槛 | **只停纯语法词** | Day 35「这是」+「一个」 |
| ⑤ 真词意外撞车 | 正文用了某个真词，恰好和测试串重合 | **改文案换同义词** | **Day 36「绝对」** |

⑤ 是这轮新加的。它的特殊之处：**不能靠停用表解决，也不能靠补内容解决**，只能换一句话说。

## 五、顺手修的 tag 越界（types ①）

排查「车位被占」时发现，词命中的是 `chewei-gui-shui`（小区车位到底归谁），而不是新建的 `chezhu-yiwo`（车位被邻居占着怎么办）。

看 tags 就明白了——旧卡的 tags 里写着：

```python
["车位归属", "产权车位", "人防车位", "占用道路", "车位出售", "占车位", "车位被占", "乱停车"]
```

但那张卡讲的是**车位产权归属**，全程没有一句在讲「车位被别人占了怎么办」。`占车位`、`车位被占` 是典型的 **tag 越界**：写 tag 时按「跟车位有关」联想，而不是按「这张卡讲了什么」。

删掉这两个 tag，词就正确落到新卡上。

**但删完发现组 C 的护栏词 `占车位` 漏召回了。** 这是好事——说明护栏起作用了。新卡 tags 里写的是「占用车位」（书面），口语是「占车位」。补上口语别名后两个词都正常：

```python
# "占车位" 是口语说法（组 C 的护栏词就是它），"占用车位" 是书面说法，两个都留
"tags": ["车位", "占用车位", "占车位", "车位被占", "挪车", "业主", "物业", "排除妨害", "车库"]
```

**这条经验记下来：tags 兼作口语别名，书面词和口语词要同时收。**

## 六、新加的工具：`db/exec.py sql`

排查过程中需要直接查库（`hay_core` 到底命中了哪个片段），但 `exec.py` 只有 `schema` / `seed` / `verify` 三个模式，`verify` 里写死了六条固定查询。

加了个 `sql` 模式：

```bash
python db/exec.py sql "SELECT ..."
```

只做只读查询（注释里写明了别用它跑写语句，写操作走 seed/schema）。以后排查「某个搜索词为什么命中某张卡」，不用再临时改脚本。
