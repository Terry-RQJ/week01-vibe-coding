## 1. 为什么要做这件事

Day 31 修搜索假命中时，有两个词卡在一个尴尬位置：

| 词 | 现象 | 当时的处理 |
|----|------|-----------|
| 装修合同 | 模糊检索召回 1 条（靠消保法「合同」字样凑够门槛） | 登记进白名单，容忍 1 条 |
| 身份证被冒用 | 同上，靠「身份证」三字召回借贷类某张卡 | 登记进白名单，容忍 1 条 |

当时的判断是「和『搬家公司』在统计特征上无法区分，再修就得引入分词/IDF，收益低».

但 Day 32 复盘时想清楚了一件事：**这不是算法问题，是内容问题**。这两个场景都是普通人真的会遇到的：

- 找装修公司签合同，被「按实际发生计算」这种开口条款坑了
- 身份证丢过一次，后来征信上莫名多出一笔贷款

内容库里**本来就应该**有这两张卡。补上之后，搜索自然就对了——不用动一行检索代码。

> **原则**：白名单只能用来过渡，不能用来常驻。往里面加词时必须同时写清「打算什么时候补内容」。

## 2. 法条核验（本日最花时间的部分）

新卡的法条全部逐条比对官方源，`source_url` 实测 HTTP 200 且页面确含该条文。

### 2.1 装修合同 → 承揽合同章

第一版我准备用**民法典第 1191 条**（用人单位对工作人员致损的责任），查完发现不对——那条讲的是「员工执行工作任务」，装修公司是独立承揽人，适用的是**第 1193 条**：

> 承揽人在完成工作过程中造成第三人损害或者自己损害的，定作人不承担侵权责任。但是，定作人对定作、指示或者选任有过错的，应当承担相应的责任。

**这个区别对用户很重要**：1191 条意味着「公司全兜」，1193 条意味着「你自己选人有错也要担一部分」。写错条号等于给用户错误预期。

最终三张法条：

| 条号 | 作用 |
|------|------|
| 《民法典》第 770 条 | 定义承揽合同（装修属于承揽） |
| 《民法典》第 781 条 | 成果质量不合格 → 可要求修理、重作、减价、赔偿 |
| 《消费者权益保护法》第 8 条 | 知情权 → 报价单必须写清品牌型号单价 |

### 2.2 身份证被冒用 → 身份证法 + 个人信息保护法

| 条号 | 作用 |
|------|------|
| 《居民身份证法》第 17 条 | 冒用他人身份证 → 罚 200~1000 元或拘留 10 日以下 |
| 《民法典》第 1165 条 | 过错责任的一般条款 |
| 《个人信息保护法》第 69 条 | **过错推定**：处理者证明不了自己没过错就要赔 |

第 69 条是这张卡最有价值的一条——它把举证责任**从受害者身上挪到了机构身上**。普通人不用证明「银行有错」，银行得自证清白。

### 2.3 源地址都实测过

```
https://www.12371.cn/...ARTI1591021670041266.shtml   HTTP 200  民法典全文
https://www.gov.cn/gongbao/content/2003/content_62254.htm  HTTP 200  身份证法全文
http://www.npc.gov.cn/npc/c2/c30834/202108/t20210820_313088.html  HTTP 200  个保法全文
```

⚠️ **身份证法那个源注意版本**：政府网公报页挂的是 2003 年主席令版。2011 年修正只动了附则的工本费条款，第十六~十九条的条号与文字与现行版一致（已逐字比对）。这条备注写进 `SRC` 字典的注释里了，免得后人看到 2003 就以为过期。

## 3. 写卡时踩到的一个「假相关」

新卡第一版 tags 里有 `"装修押金"`。结果搜「押金」时它冒出来了——但那张卡讲的是**签合同、防增项、验收**，压根没讲装修押金。

这是典型的「为了覆盖搜索词而硬塞标签」。删掉之后：

| | 搜「押金」 |
|---|---|
| 删之前 | 3 条（定金/订金、房东不退押金、**装修合同**） |
| 删之后 | 2 条（定金/订金、房东不退押金） |

**教训**：`tags` 兼作口语别名（Day 30 的约定），但别名必须是**这张卡真的在讲的东西**。为了搜索覆盖加标签，等于制造新的假命中——刚修完假命中就自己造一个，很讽刺。

## 5. 顺手修掉一个「每次加卡都要改」的硬编码

`docs/day29-verify-online.py` 里写死了 `TOTAL_EXPECT = 122`。Day 30（121）、Day 31（122）、Day 33（124）各改一遍，漏改就误报 5 项失败。

改成从 `data/cards.js` 读真数：

```python
def _expected_total():
    """从 data/cards.js 读卡片真数，而不是在本脚本里写死。"""
    import os, subprocess
    root = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
    js = os.path.join(root, "data", "cards.js")
    code = ("const vm=require('vm'),fs=require('fs');const sb={window:{}};"
            "vm.createContext(sb);vm.runInContext(fs.readFileSync(process.argv[1],'utf8'),sb);"
            "process.stdout.write(String(sb.window.LAW_CARDS.length));")
    out = subprocess.run(["node", "-e", code, js], capture_output=True, text=True, timeout=30)
    if out.returncode == 0 and out.stdout.strip().isdigit():
        return int(out.stdout.strip())
    print("（读取失败，回退默认值 124）")
    return 124
```

**为什么用 node 执行而不是正则**：`cards.js` 结尾还挂了 `window.LAW_CATEGORIES = [...]`，正则抠 `window.LAW_CARDS = [...]` 容易截错，而且里面有中文引号与转义。执行一遍最稳。

读不到时退回 124 **并打印原因**，避免静默变成「永远碰巧通过」。

## 6. 项目书也一起更新了

`法律小科普轻站-项目书.docx` 里写着「122 张 / 261 条」，是交付材料，数字不改会误导。

改法：先改 HTML 源（`output/brief-compose/*.html`）→ 重新转换 docx。

转换时首次被 preflight 拦下：

```
[PF-01] 缺少 <style> 块——页面级规则（@page/命名页）必须写在 <style> 内
```

上次生成时代码是靠 `--no-preflight` 跳过的，等于留了个隐患。这次补了合规的 `<style>`：

```html
<style>
  @page { size: A4; margin: 2.2cm 2.4cm; }
  body { font-family: SimSun, serif; font-size: 12pt; color: #333333; }
  p { line-height: 1.7; }
  table { border-collapse: collapse; width: 100%; }
</style>
```

转换结果 `success: true`，内容 24 段缺失 0，docx 内「124 张」×2、「267 条」×2，旧数字 0 处残留。
