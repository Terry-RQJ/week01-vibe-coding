## 1. 怎么挑「最高优先级卡点」

### 1.1 三级分类（先分类，再排序）

| 级别 | 名字 | 判据（客观，不含"感觉不好"） | 今日是否修 |
|---|---|---|---|
| **P0** | 阻断 | 核心流程**走不完**：点了没反应 / 白屏 / 出红字报错 / 需要人帮忙才过 | ✅ 必须修 |
| **P1** | 卡住但有绕过 | 停了 > 5 秒、找不到入口、文案看不懂但自己摸索过去了 | ✅ 修一个（今日主任务） |
| **P2** | 体验瑕疵 | 没耽误他完成流程，但他说"有点别扭 / 不好看 / 想改配色" | ❌ 今日不做，记账 |

> 分类只看**行为**，不看语气。试用者笑着说"挺好玩的，就是我没找到"，那也是 P1。

### 1.2 同级别内的排序判据

按顺序比，前一条打平才看下一条：

1. **是否挡住"核心操作"** —— 核心操作 = 「收藏」（第 3 步）。挡住它的排最前。
2. **是否多个试用者都会遇到** —— 只有一个人遇到 + 他那台设备特有 = 降一级。
3. **是否与"我以为会这样"有关** —— 即"文案/位置与用户预期不符"，比"功能缺失"更容易修、收益更大。
4. **能不能今天修完** —— 若需要改架构（本项目无架构可改，纯静态 + 云函数），换下一个。

### 1.3 今日红线（来自任务"今日不做"）

- ❌ 不按反馈大改
- ❌ 不加新功能
- ✅ 只修**一个**最高优先级卡点，其余全部写进"记账"清单留给后面

### 1.4 挑完之后先写这一句

> 最高优先级卡点：**第 __ 步 —— __**。
> 分类：P0 / P1。判据：__（对应 1.1 哪一条 + 1.2 哪一条）。
> 不修的理由（给其他卡点）：__。

## 2. 修复提示词模板

> **沿用 Day 24 的格式**：现象 → 复现步骤 → 已尝试动作。
> 用法：把 `{ }` 里的内容换成记录表里的真实内容，整段发给 AI（或填进 issue）。
> 硬要求：三段都必须有**原文**，不许出现"看起来""好像""感觉"。

```
【现象】（一句话，只说客观表现）
{在哪一步 / 什么设备上 / 用户想做什么 / 实际发生了什么}
例：在 iPhone 竖屏上，点卡片右下角的 ☆ 之后按钮没有任何变化，用户以为没点上，连点了 4 次。

【用户原话】（逐字抄，不改写）
"{记录表 B 段抄下来的原话}"

【复现步骤】
1. {设备与浏览器：例 iPhone 14 / Safari 18，竖屏}
2. 打开 {完整 URL}
3. {点了什么：例 点「劳动类」筛出第 3 张卡}
4. {再点什么：例 点该卡片右下角 ☆}
5. 观察：{预期的客观判据 vs 实际}
   - 预期：按钮文案变为「★ 已收藏」
   - 实际：{原文照抄，如仍是「☆ 收藏」，控制台报 xxx}

【已尝试动作】（做了哪些排查，各自结果）
- 换设备：{例 Edge 桌面端 → 正常变 ★，只在 iPhone Safari 上不复现}
- 换入口：{例 从详情页点收藏 → 同样无反应 / 正常}
- 看控制台：{例 报 `xxx is not a function` / 无报错}
- 刷新后再试：{例 刷新后 ☆ 变成 ★，说明数据写进去了，只是 UI 没更新}
- 换网络：{例 手机流量 → 一样}

【边界】（今日红线，别顺手扩张）
- 不改信息架构、不加新功能、不动与本次卡点无关的文件
- 若能最小改动解决就最小改动

【验收标准】（一条可观测的判据，不是"看起来正常"）
{例：iPhone Safari 竖屏下点 ☆ 后 500ms 内按钮文案变为「★ 已收藏」，
 且刷新后仍为「★ 已收藏」，且「我的收藏」页出现该卡}

【产出要求】
- 给出改动文件清单（含该文件属于哪一天的产物）
- 给出改前后的对照证据（截图或命令行原文）
```

### 2.1 填好的示例（**占位**，等真实反馈替换）

> ⚠️ 下面这段是**格式示范**，不是真实结论。真实内容必须来自 `docs/day27-feedback-form.md`。


## 3. 修复后：请对方复验的最小任务

> 原则：**不超过 3 步、只说点什么、只说能一眼看出对错的**。
> 不要让他重跑整条链路（浪费他时间，也测不出聚焦信息）。

### 3.1 模板（整段发给试用者）

```
刚才那个问题我改了一下，麻烦你再花 1 分钟确认一下，只有 3 步：

1. {复现条件：例 用你刚才那部 iPhone，竖着拿，打开同一个链接}
2. {原来的那一步：例 点第 1 张卡片右下角的 ☆}
3. {说出可观测的判据：例 告诉我按钮上的字变成了什么？}

如果还是老样子，直接说"没好"就行，我要的就是这个。
```

### 3.2 复验时要一起收回的信息

| 问什么 | 为什么要 |
|---|---|
| 按钮上现在显示的字 | 唯一判据，别用"好了吗"这种问题 |
| 有没有弹出一小条提示 | toast 是第二个观测点 |
| 刷新一次，字还在吗 | 区分"UI 改了"和"数据存了" |
| 还是那台设备吗 | 换设备就说明不了问题 |
| 截图/录屏 | 存在**他的设备上**才算证据 |

### 3.3 复验通过 / 不通过之后

- **通过** → 把复验截图与逐字回复补进记录表 D、E 段，然后才提交推送。
- **不通过** → 不要重复问，回到第 2 节，用**新的"已尝试动作"**重写提示词（把"用户复验仍失败"作为一条新证据写进去）。
